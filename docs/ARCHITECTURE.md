# Architecture

The persistent Go/Win32 engine owns the tray icon, taskbar materials and per-user settings. It waits for Windows messages. Version 1.1.2 opens an on-demand GDI+ panel and releases its process on dismissal. The older WebView2 path remains available for comparison with --css-preview/--css-check.

Taskbar materials use the ExplorerTAP COM interface with checked HRESULTs. CSS commands are posted asynchronously to the engine and acknowledged after completion; this avoids synchronous input COM-call failures. Allowed commands are explicitly listed in menu_css.go. The menu has no HTTP listener, remote page, external font, or arbitrary command bridge.

The native panel paints premultiplied ARGB into a reusable DIB and presents it with UpdateLayeredWindow/AC_SRC_ALPHA. Empty corners have zero alpha; the panel tint has 18% alpha. No redirected WebView or native accent backdrop sits behind the panel. It is live translucency, not a frozen desktop picture. Menu backdrop blur is not implemented; taskbar Glass/Acrylic effects remain unchanged. Native and WebView probes both produced opaque backgrounds under the previous host configuration, so the issue was not conclusively isolated to WebView2 alone.

One finite timeline animates the popup, blue selection plate and switch thumbs. A high-resolution ticker posts at most one outstanding frame up to 120 Hz and stops at the endpoint; timer resolution is restored afterward. Font and bitmap resources are reused while the panel is open. Outside-click and overflow-hide hooks exist only during the visible helper lifetime.

Foreground contrast adapts to bright/dark backgrounds with hysteresis. Four unobstructed corner pixels are sampled every 500 ms only while the panel is open; no desktop images are stored or transmitted. The helper exits after its close transition, so sampling and GDI+ resources do not remain in the idle engine. Keyboard Tab/Shift+Tab and Enter/Space are supported; native screen-reader integration is not yet implemented.

Mode and switch feedback is immediate. One engine command is in flight at a time; rapid input retains the latest intended state. Acknowledgements reconcile actual settings, and errors roll the controls back without a retry loop. Unchanged native host/border calls are skipped, with invalidation on theme/display/color changes and explicit refresh.

Preferences are stored in LOCALAPPDATA/Senja/settings.ini. Startup uses the current-user Run registry key. The update button starts Senja-Update.exe on demand; the idle engine does not import the HTTP client. The worker reads this repository's latest stable release API, rejects same/older versions, validates repository/tag-specific asset URLs and HTTPS redirect hosts, downloads within size/time limits, and verifies the EXE against SHA256SUMS.txt before launching it. Failed temporary downloads are removed. The installer performs the existing graceful engine replacement, retaining settings and enabled startup. No automatic update polling runs. A second click during a check/download is ignored. Native menu progress is reported through bounded phase messages; the worker exits on completion. Release checksums protect transfer integrity, not against a compromised release account; releases remain unsigned.

Senja-Bar.exe embeds the portable ZIP, extracts it once into a version-and-content-addressed LOCALAPPDATA/Senja/app folder, starts the engine, and exits. Extraction checks paths and required files and publishes only a complete staging directory. An older running engine exits gracefully before replacement. An already enabled startup preference follows the new engine path. No administrator access or resident launcher is needed.

Unmodified dependency hashes and source provenance are in DEPENDENCIES.json. The legacy cmd/samar path is internal only.
